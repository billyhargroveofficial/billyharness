# Generated Reference And Docguard Strategy

This is a handwritten design note for future `docsgen` and `docguard`
implementation. It is not generated output and it is not an implementation
backlog. The generated references described here are machine-oriented snapshots
for agents; stable architecture rules remain in `docs/`.

## Reference Set

Future `fast-agent-harness docsgen` output should live under
`agent-index/generated/` unless a human-facing reference tree is introduced
later. Each reference should be deterministic, compact, and traceable to source
files.

## Generated Markers

Whole generated files should start with this marker shape:

```md
<!-- Code generated by fast-agent-harness docsgen; DO NOT EDIT.
Generator: fast-agent-harness docsgen <target>
Source-Globs:
  - internal/protocol/*.go
Command: fast-agent-harness docsgen <target> --out agent-index/generated/<target>.md
Generated-At: 2026-07-03T00:00:00Z
Source-Commit: <git commit>
Dirty-At-Generation: false
Source-Hash: <sha256 over normalized matched source contents>
-->
```

Generated sections inside handwritten files should use stable paired markers:

```md
<!-- BEGIN GENERATED: name -->
...
<!-- END GENERATED: name -->
```

Generated section metadata may be compact, but it must be recoverable from the
manifest. A section generator should refuse to write when the begin/end marker
pair is missing, duplicated, nested, or renamed unexpectedly.

## Source Globs

Every generated reference needs source globs in two places: the file marker and
`agent-index/docs-manifest.json`. The globs are part of the freshness contract.
They should include:

- direct source files that define the documented surface;
- generator-owned helper files once docsgen code exists;
- tests only when tests define fixtures, golden protocol traces, or documented
  compatibility behavior that cannot be derived from production code;
- handwritten canon only when the generated output intentionally cross-checks
  or summarizes it, as with package maps.

Globs should be narrow enough that unrelated dirty files do not mark an
unrelated generated reference stale. For repo-wide outputs such as
`repo-map.md`, broad globs are acceptable because the output is meant to move
with the whole repository.

## Dirty At Generation

`dirty_at_generation` means the generated snapshot may include facts from files
that are not represented by a clean commit.

The top-level manifest field describes the whole worktree when the manifest was
created. Per-document fields should describe that document's source scope:

- `dirty_at_generation=false` means `git status --porcelain -- <source globs>`
  and the docsgen implementation files were clean at generation time;
- `dirty_at_generation=true` means at least one matched source file, generated
  output file, manifest entry, or docsgen implementation file was dirty;
- generated docs should also record `source_commit` and `source_hash` so a
  clean source change can be detected even when timestamps are misleading;
- when dirty is true, the manifest should include a bounded `dirty_paths` list
  for the affected target, with secrets and runtime artifacts excluded.

Untracked runtime artifacts under `$BILLYHARNESS_HOME`, session stores, caches,
or tool output directories should not affect generated-reference dirtiness
unless the target explicitly documents those artifacts.

## Temp-Dir Diff Verification

Verification should avoid dirtying the worktree by default. The future check
mode should:

1. create a temporary output root;
2. generate the requested references into that root;
3. compare temp output with checked-in output byte-for-byte after normalizing
   trailing whitespace and final newlines;
4. report added, removed, changed, and stale generated files;
5. leave the worktree untouched unless an explicit write mode is requested.

The intended command shape is:

```sh
fast-agent-harness docsgen --check
fast-agent-harness docsgen --check --target protocol-events
fast-agent-harness docsgen --write --target protocol-events
```

`--check` should be suitable for `go test` and CI. `--write` should be a local
maintenance command and should update file markers plus manifest metadata
together.

## Docguard Strategy

Future `docguard` should be a focused Go test package separate from the
existing architecture import guard. It should inspect documentation and index
metadata without importing runtime packages.

The first checks should cover:

- local Markdown links: relative file links must resolve, repo-local anchors
  should match headings when practical, and generated files should not link to
  runtime artifacts;
- forbidden active-work language: canonical `docs/` files must not contain
  active implementation checklists, goal prompts, completion evidence sections,
  or runbook-style command transcripts; legacy research can be lower severity
  or allowlisted by manifest status;
- manifest coverage: every canonical doc linked from `llms.txt`,
  `docs/README.md`, `.agents/rules/README.md`, or `agent-index/README.md`
  should have a manifest entry, and every manifest path should exist;
- ADR status: ADR filenames should keep unique zero-padded numbers, statuses
  should be one of `proposed`, `accepted`, `superseded`, or `deprecated`,
  superseded ADRs should link to their replacement, and the ADR index should
  mention each ADR file;
- stale docs: generated docs should compare current source hashes against
  manifest/file-marker hashes, while hand-curated docs should compare
  `last_reviewed`, `related_code`, and recent source changes to produce a
  warning rather than a hard failure at first.

Docguard should keep generated-reference drift and architecture-import drift as
separate signals: architecture drift remains enforced by
`internal/architecture`; documentation/index drift belongs to docguard.

## Manifest Shape

Generated-reference entries should extend the current document metadata with
fields like these:

```json
{
  "path": "agent-index/generated/protocol-events.md",
  "kind": "generated-reference",
  "status": "generated",
  "generated": true,
  "generator": "fast-agent-harness docsgen protocol-events",
  "source_globs": ["internal/protocol/*.go", "internal/eventlog/*.go"],
  "source_commit": "<git commit>",
  "source_hash": "<sha256>",
  "dirty_at_generation": false,
  "last_generated": "2026-07-03T00:00:00Z",
  "trust_level": "generated_from_source"
}
```

Handwritten planning/design files, including this one, should keep
`generated=false`, `trust_level=hand_curated`, and `last_reviewed`.

## Future Implementation Areas

Docsgen can begin as small source extractors for CLI flags, gateway routes,
config specs, protocol events, and static tools. The package map can reuse the
existing `internal/architecture` parser and `go list -json ./...`. Docguard can
start with local link and manifest coverage checks before enforcing staleness
strictly.

These implementation areas should become loop work only when Billy asks for a
new implementation slice.
