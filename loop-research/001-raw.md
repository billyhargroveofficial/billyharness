Iteration 11: Foreground shell output is bounded only after unbounded in-memory capture

Finding: foreground `shell_exec` advertises and reports `max_output_bytes`, but it uses `exec.Cmd.CombinedOutput()` first, which buffers the entire stdout/stderr stream in memory before Billyharness truncates, stores an output ref, or returns metadata. - `internal/tools/shell_process.go:228-249` normalizes `MaxOutputBytes` before execution.
- `internal/tools/shell_process.go:293-299` runs foreground commands with `cmd.CombinedOutput()` and converts the returned full byte slice to `rawText`.

- `go test ./internal/tools` passes from cache, so this is an uncovered stability gap.

- `max_output_bytes` is a response-size limit, not a process-output memory limit, despite looking like one in the tool contract and metadata.

- Debuggability is misleading because a successful truncated result says the budget was enforced, but the expensive allocation already happened.

Test shape:
- Replace `CombinedOutput` with stdout/stderr pipes copied through a bounded writer that stores full output to an output ref incrementally or stops retaining after a hard cap.
- Add a regression test with a command producing output far above `max_output_bytes`; assert retained memory/returned output stays bounded and metadata reports `output_bytes` as observed or capped.
- Make metadata distinguish `inline_budget_bytes` from a true `capture_budget_bytes` so operators know which limit protected memory.
